# AI 开发流程

围绕功能建立规格，以相关模块的现有代码理解具体实现。人确认业务目标、关键规则与预期结果；AI 整理需求、补齐边界、设计架构、开发、测试、审查并同步文档。

## 范围与分工

- 优先采用当前对话已经明确的决定，不重复请求确认。仅对尚未决定、会影响业务行为或用户权益的取舍提出问题，并附推荐方案和影响。
- 技术选择由 AI 负责。技术选择改变已确认的业务行为、超出已确认预算或交付范围时，将其转成用户能判断的业务问题；既定范围内的常规实现选择自行处理。
- 用户只要求讨论、编写文档或拆分需求时，完成对应工作；只有实现已获授权时才修改代码。文档中的计划不自动授权执行。
- 保持文档精简。产品背景只保留理解功能所需的用途与范围，不默认编写市场分析、用户画像或长篇 PRD。
- 尊重仓库已有规则与文档路径。有等价文档时原地维护并建立对应关系，不强制迁移目录或创建重复规格。

## 三级文档

```text
docs/
├── project.md
├── architecture.md
├── modules/
│   └── <module>.md
└── features/
    └── <module>/
        └── <feature>.md
```

| 层级与文件 | 维护内容 | 责任 |
|---|---|---|
| 项目级 project.md | 一两句用途、基本功能、范围、模块索引 | AI 整理，人确认功能范围 |
| 项目级 architecture.md | 技术栈、整体架构、架构原则、全局代码规范 | AI 负责，业务相关取舍由人决定 |
| 模块级 modules/ | 模块职责、对外能力、核心业务规则、依赖、接口约束、功能索引 | AI 维护，人确认业务规则 |
| 功能任务级 features/ | 功能用途、本次目标、输入输出、行为、边界、验收标准及必要设计 | AI 起草，人确认业务预期，AI 实现与验证 |

创建或补齐某类文档时，读取对应模板并按项目裁剪；不一次加载所有模板。

- [项目模板](assets/project.md)：建立项目功能概览时使用。
- [架构模板](assets/architecture.md)：建立全局技术约束时使用。
- [模块模板](assets/module.md)：划分模块或描述模块长期能力时使用。
- [功能模板](assets/feature.md)：拆分或变更具体功能时使用。

模板中的占位内容须替换，示例路径须按实际文件位置调整。可选且不适用的章节直接省略。不要将模板空壳当作已完成需求。

## 文档粒度与事实来源

- 预期行为与验收依据来自已确认的功能规格；模块公共规则、依赖和接口来自模块文档；全局约束来自架构文档；当前实现细节来自代码。
- 文档设计最多展开到模块协作、状态机、数据库实体或表的字段语义与关系、唯一性和一致性约束。仅在有助于解释行为或跨边界约束时添加。
- 不在文档中预写实现代码、类定义、函数体、内部辅助结构或逐文件编码步骤。对外接口可描述输入输出、错误语义、兼容要求；已有机器可读接口定义直接引用。
- 读取实现时，先定位相关模块、调用方与验证代码，再按依赖扩展。无需先阅读整个代码库，也不维护一份代码镜像文档。
- 公共规则在所属层级定义一次，下层引用。项目列基本能力，模块列功能，功能写具体行为，不逐层复制细节。
- 用户当前明确要求是本次变更依据，现有规格提供基线。发现用户要求、不同层级文档或代码之间有冲突时，列明受影响的规则并同步解决；不能用旧文档否定已明确的新要求，也不能把现有实现自动当作业务意图或修改验收标准来迁就错误实现。

## 工作流程

### 1. 确认范围与现状

读取仓库规则、项目概览、架构约束、相关模块及功能文档，然后检查相关代码。区分用户要求的是讨论、文档整理、实现，还是已授权变更的继续执行。

已有项目缺少文档时，按当前任务补齐必要上下文，不要求先整理整个项目。由代码提取的行为注明是观察到的现状；无法确认的业务意图单列待决，不推断成已确认需求。

新项目按基本功能划分模块，再按可独立验收的完整行为拆功能；每份功能文档应能驱动一次合理规模的开发任务。规模过大时按业务行为拆分，不按 Controller、Service 等代码层拆任务。插件、配置、日志等仅为可选示例，不默认创建这些模块。

### 2. 提出变更清单

简要列出业务行为变化、受影响功能与模块、待更新文档。变更涉及调用方、接口兼容或存量数据时，说明影响及处理方案。

用户已明确的要求直接落实。未决业务问题集中提出，说明选项、推荐与影响；可继续无依赖工作，不替用户默默决定关键规则。技术细节自行判断。

### 3. 更新规格

先写清目标、输入输出、已识别的正常行为、边界及可观察的验收结果，确定基本测试逻辑，再进行实现。按下方约定检查并补充必要的基础设计。

同一功能长期维护同一路径的规格。修改原文档，不生成 feature-v2.md 或以日期命名的重复需求。功能重命名或移动时同步索引和引用。

功能状态使用“规划中 / 开发中 / 已实现”，分别表示尚未实施、正在实施、已在当前代码版本实现并通过适用的技术检查。“已实现”不表示已部署或已获人工验收；验收情况另行记录。索引按能力或功能标注，模块有混合状态时注明范围。

尚未实现的规格可直接修改；开发中的需求变化须检查已有部分实现并调整范围。对于已实现功能的修改或删除，在原文件中临时增加“本次变更”章节，保留当前有效规格，记录目标差异、变更状态与目标验收标准，顶层功能状态保持“已实现”。本次任务以目标差异覆盖的条款和未改变的原规格共同作为验收依据。

受影响的项目、架构、模块规则也要区分当前与目标。尚未落地的公共规则在所属文档的“本次变更”章节定义一次，功能文档链接到该目标条款；完成后一起合并到正文，并修正指向临时章节的链接。连续调整同一次变更时更新该章节，不追加多套互相冲突的目标。

### 测试与基础设计约定

- 针对当前已识别且与功能相关的正常、边界和异常场景设计测试，明确本次覆盖范围及已知缺口。不要求穷举所有边界或达到统一覆盖率；未覆盖不能宣称已验证，新发现的相关场景按影响补充。
- 编写规格时检查输入、权限、状态、数据、重复与并发、依赖失败和恢复等适用维度，说明条件、处理及可观察结果，包括失败后的数据状态、副作用和重试行为。未决定的业务规则列为待决。
- 每个功能检查状态转换、持久化数据和跨模块协作是否涉及必要设计。涉及时说明转换条件、数据语义与关系、一致性约束或协作失败处理；共享设计归模块，系统级约束归架构，功能引用并说明自身差异。文字或表格能说明清楚就使用文字或表格，复杂关系再用 Mermaid 状态图、ER 图或时序图，不强制每个功能画图。
- 基本函数逻辑和可隔离业务规则用自动化单元测试；复杂交互、接口与持久化协作用自动化集成测试。可用简单 mock 客户端调用真实后端，记录真实运行与模拟的依赖范围；自动化执行并断言结果，不能将模拟响应视为真实后端已验证。
- 能可靠自动化验证的场景优先自动化，包括可自动化的 UI 交互。手工测试仅补充自动化难以覆盖或需要人工判断的部分，并说明原因；人最终负责兜底业务验收。手工技术测试与人工业务验收分别记录。
- 功能文档只保留基本测试逻辑：覆盖哪些行为、选择何种测试方式、必要环境与模拟范围、回归范围及测试入口。具体自动化数据、步骤和断言保留在测试代码中；手工用例须提供可复现的前置条件、步骤和预期结果，较多时拆分文件并链接。
- 每个自动化测试和手工用例都有稳定编号，沿用项目已有约定，否则采用下方格式。自动化编号写入测试名称或元数据，关联相应验收标准；手工编号写入用例文档。验收标准编号（如 AC-01）与测试编号分别维护，可一对多关联。

测试编号格式：`<模块标识>-<功能标识>-<类型>-<序号>`；参数化场景使用 `<基础编号>-<场景标识>`。

| 字段 | 约定 | 示例 |
|---|---|---|
| 模块标识、功能标识 | 使用稳定的小写英文标识，可含数字，多个单词用连字符连接；组合在项目内唯一 | order、cancel |
| 类型 | UT 为自动化单元测试，IT 为自动化集成测试，MT 为手工测试 | UT |
| 序号 | 在同一模块、功能、类型内从 00000001 递增，固定八位，不足八位时前补零 | 00000001、00001000 |
| 场景标识 | 仅参数化场景使用，采用有语义的小写英文标识，多个单词用连字符连接；在同一基础编号内唯一，不使用参数排列位置 | empty-input |

例如：`order-cancel-UT-00000001`、`order-cancel-IT-00000001`、`order-cancel-MT-00000001`；参数化实例为 `order-cancel-UT-00000002-empty-input`、`order-cancel-UT-00000002-invalid-status`。参数化测试代码保留基础编号，执行报告应能区分场景后缀。

编号不因排序、文件移动或功能显示名称变化而改变。相同测试目的的预期随需求调整时保留编号；新增独立场景分配新编号或新的参数化场景标识。废弃编号不得分配给其他用例，序号允许有空缺；确需迁移编号时同步引用并保留映射。

- 每项验收标准明确验证方式和执行状态，可关联一项或多项测试，不要求三种方式重复覆盖。用例已编写不代表已执行；失败、未执行、环境阻塞和已知覆盖缺口如实记录。
- 需求变化时同步检查验收标准、基本测试逻辑、自动化测试和手工用例，明确保留、新增、修改、废弃及回归范围。文档任务只更新测试计划，实际测试代码在授权实现时同步。已实现功能的目标测试变化记录于“本次变更”，保留当前依据，落地后合并。旧通过记录仅证明旧版本，受影响的新行为重新验证；不得修改预期来迁就错误实现。

### 4. 实现与验证

仅在用户授权实现的范围内执行。AI 根据现有代码自主决定实现细节，执行适当的测试和代码审查；可使用适合当前任务的审查技能，但不依赖特定外部技能才能运行本流程。

按功能验收标准和测试方案验证行为，执行受影响的自动化测试及必要回归，并检查受影响调用方。本次必要技术检查通过后才可标记为已实现；存在必要检查失败或阻塞时保留开发中状态（已有功能则保留本次变更）。技术检查与人工业务验收分别记录，未实际验证的项目如实说明。实现中发生业务规则变化时先解决相关决定，再更新规格与实现。

### 5. 同步与交付

实现并通过相应技术验证后，将本次变更合并到长期规格，清理临时变更章节，并将本次验证结果记录到更新后的规格。人工业务验收若尚未进行，明确记为待验收，不宣称验收通过。删除功能则按下表处理，并将删除验收结果保留在交付说明或已有 PR 中，避免证据随文件消失。

仅完成文档任务时，新功能或本次变更保持“规划中”，已有功能的顶层状态不变。按用户请求的范围报告文档工作完成，不把尚未授权的开发当作必须继续执行的工作。

文档与代码作为同一交付单元，在同一变更集或 PR 内保持一致；无需为同步规则自动创建提交或发布。最终简要报告行为变化、验证结果、更新的文档、经检查无需修改的层级及剩余业务决定。

## 新增、修改、删除的同步规则

| 变更 | 功能文档 | 模块文档 | 项目与架构文档 |
|---|---|---|---|
| 新增 | 新建一份规格，明确状态 | 增加功能链接与对外能力；公共规则、依赖或接口发生变化时更新 | 影响基本功能、项目范围或模块清单时更新 project；影响全局技术约束时更新 architecture |
| 修改 | 尚未实现的规格直接改；已实现的规格通过本次变更章节区分现状与目标 | 仅同步受影响的职责、公共规则、能力、依赖及接口；未落地变化单独标明 | 仅在影响该层内容时更新；未落地变化单独标明 |
| 删除 | 已实现功能先说明待删除范围与验收；实际删除并验证后移除文件。部分删除则保留并修订规格 | 待删除时保留当前能力并标记计划；完成后移除能力、链接和失效规则，修正依赖 | 待删除时标记计划；完成后移除失效的基本能力、模块或架构描述 |

- 上下层和调用方按实际影响同步。局部字段校验变化通常只影响该功能；成为模块公共规则时才上移。
- 删除前检查引用、依赖和存量数据。删除功能不等于授权删除生产数据；未决定的数据处置或兼容策略单独提出。
- 取消尚未实施的需求时，检查确认没有相关实现后直接移除规划规格及引用；已有部分实现时先处理其影响。撤销已实现功能的待实施变更时，移除目标差异并恢复相关规划引用，保留当前规格；若已开始实施，同时处理代码中的部分变更。
- 仍提供兼容服务的功能标记为弃用并保留规格，待真实移除后再删除文档。不能因文档删除就宣称功能已经移除。
- 已提交的历史由 Git 保存，不另建持续累积的历史需求副本。删除前确认历史确实可恢复；未提交或无版本控制的唯一内容先保留可恢复副本，并明确其为历史，不列入当前功能索引。
- 模块和项目索引里的规划能力必须带状态。实现完成后同步索引，避免把计划能力列为已实现。
- 纯内部重构且外部行为、公共约束均未变化时，不改写业务规格；仍检查是否影响架构约束。

## 完成检查

按本次授权范围检查；文档任务不要求先实现代码。

- 功能规格和验收标准反映已确认的要求，当前能力与待实现变更可区分。
- 受影响的模块规则、依赖、接口、全局约束已同步；未受影响的文档无需改动。
- 索引与链接有效，同一功能没有互相竞争的规格，删除和重命名没有遗留引用。
- 已交付行为有相应验证证据；验收标准有验证方式及执行状态，自动化测试与手工用例有稳定编号，需求变更已同步测试。未验证、覆盖缺口和待人工验收项未伪装成完成。
- 文档没有下沉到具体实现代码；技术实现质量由实际代码审查和测试检查。
